# Nyanithm Controller V3 · Linux (Wine / Proton) 使用说明

给在 Linux 上跑 CHUNITHM 的 Nyanithm 手台用户。解决的核心问题是：

> **手台直连 Wine 的 COM 口时输入明显延迟——按下去慢半拍、松手后游戏还保持按下、
> 打歌时该 CRITICAL 的偶尔变成 ATTACK。**
>
> 但同样的手台在厂商网页配置工具里却毫无延迟。

原因是 **Wine / Proton 的串口读取路径**，不是手台、不是 Linux、也不是游戏渲染。
本目录的 `serial_relay.py` 在宿主侧替游戏收发数据，绕开这一层。

---

## 一、它能解决什么，不能解决什么

| 症状 | 中继能否解决 |
|---|---|
| 按下去要等一下才有反应 | ✅ |
| 松手后游戏还显示按下 | ✅ |
| 打歌像有 100ms+ 延迟 | ✅ |
| 偶发 ATTACK（一局里几个） | ⚠️ 只能缓解，见第七节 |
| 手台本身的灵敏度 / 阈值 | ❌ 请用厂商网页校准 |

---

## 二、前置条件

1. 设备能被系统认出来：

   ```bash
   ls /dev/serial/by-id/ | grep -i nyanithm
   # usb-NyaLab_Nyanithm_Controller_V3_<序列号>-if02
   ```

2. 当前用户有串口权限（Arch 是 `uucp` 组）：

   ```bash
   groups | grep -q uucp || sudo gpasswd -a "$USER" uucp   # 之后重新登录
   ```

---

## 三、建好 COM 映射（只需要做一次）

Wine 会默认给前缀建 `com1..com32 -> /dev/ttyS0..31`，这些口能打开但永远没数据，
而 chuniio 是从 COM1 往上扫的，所以要清掉，并把真设备放到低编号上。

```bash
DOSDEV=~/游戏前缀/dosdevices      # 改成你自己的，Lutris 一般是 <prefix>/dosdevices

# 1) 删掉指向不存在主板串口的死映射
for i in $(seq 1 32); do
  [ -L "$DOSDEV/com$i" ] && rm -f "$DOSDEV/com$i"
done

# 2) 用 by-id 建映射（不要写死 /dev/ttyACM0，设备重新枚举会变号）
ln -sfn /dev/serial/by-id/usb-NyaLab_Nyanithm_Controller_V3_*-if02 "$DOSDEV/com3"
```

一定要用 `by-id`：手台每次重新枚举，`ttyACM0` 可能变成 `ttyACM1`，
写死节点会变成悬空链接，此时 chuniio **不会报错**，只会静默退化，表现就是「又开始卡了」。

---

## 四、启动

先起中继，再启动游戏：

```bash
# 终端 1：中继（保持运行，Ctrl-C 退出时会自动还原 com）
python3 tools/serial_relay.py

# 终端 2 / Lutris：正常启动游戏
```

看到这样的输出就说明接上了：

```
中继运行中：现在启动游戏、进歌打一首，回来 Ctrl-C
  [12:00:43] 值更新  0/s  游戏请求 1348/s  积压 0/丢弃0  设备往返 2.05ms  快照 3.2ms  失败 0
```

字段含义：

| 字段 | 说明 |
|---|---|
| `游戏请求` | 游戏每秒来要几次数据（菜单里约 45/s，打歌时 1000~1500/s） |
| `设备往返` | 中继问一次手台再拿到应答的耗时，正常 2ms 左右 |
| `快照` | 这次应答用的数据有多旧，正常 < 5ms |
| `积压 / 丢弃` | 应为 `0 / 0`；`丢弃` 一旦增长说明帧被打断过 |
| `失败` | 累计超时次数，开局增长几次正常，之后应基本不动 |

## 五、阈值校准（强烈推荐）

**不要用本工具的 `--snap/--lead` 去调灵敏度**，那是补救手段。
正确做法是用厂商网页把每个键的阈值写进手台：

1. 浏览器连手台 → 「读取设置」，先把现有阈值截个图
2. 用**正常演奏的力度**逐键测试校准
3. 写入固件

校准完再用中继，**不要叠加 `--snap / --lead / --hyst`**。

## 六、参数速查

```bash
python3 tools/serial_relay.py              # 默认就够了
python3 tools/serial_relay.py --com 33     # 如果你的映射在 COM33
python3 tools/serial_relay.py --hz 250     # 询问设备的频率，默认 200
```

| 参数 | 作用 | 什么时候用 |
|---|---|---|
| `--com N` | 占用哪个 COM 号 | 映射不是 com3 时 |
| `--hz N` | 向手台询问的频率 | 默认 200，一般不用改 |
| `--trace N` | 打印第 N 格数值的每次变化（带毫秒间隔） | 检查传感器响应速度 |
| `--monitor` | 打印触摸状态和「值更新次数/秒」 | 确认手台本身是否正常 |
| `--snap N` | 把数值在 N 处二值化成 0/255 | 固件阈值无法调整时的补救 |
| `--hyst N` | 迟滞量，防阈值附近抖动 | 配合 `--snap` 使用 |
| `--lead N` | 按上升斜率提前 N 毫秒触发 | 补偿输入延迟，太大会误触 |
| `--inject N@Hz` | 注入测试：让第 N 格自己闪烁 | 判断延迟出在输入还是显示 |
| `--beep` | 注入翻转时响一声 | 配合 `--inject` 用耳朵对照 |

> `--snap / --hyst / --lead` 只是软件补救：`--snap` 越低越灵敏（容易"手没碰到就响应"），
> `--lead` 越大越跟手（同样会提前误触）。**优先用厂商网页校准，别拿这三个硬调。**

---

## 七、关于偶发 ATTACK

手台传感器固件是 **60Hz** 上报（每 16.7ms 一次），而打歌时游戏每秒要问 1400 次——
中间那 20 多次拿到的都是同一份数据。这 16.7ms 的量化是设备侧的物理上限：

- 想进一步压到街机手感，只能看厂商能不能提高上报率
- 软件侧可以用 `--snap` + `--lead` 补偿**平均偏移**，但补偿不了**抖动**

如果大部分都正常、一局只掉几个，属于这个上限，不是配置错误。

---

## 八、协议速查（想自己写 chuniio 的话）

串口 115200，CDC ACM，按「一问一答」工作，设备不主动推流：

| 主机发送 | 设备回应 |
|---|---|
| `0xB0` | `0xB0`（在线检测） |
| `0xAF` | `0x21`（API 版本） |
| `0xB1` | 33 字节：32 个传感器原始值 + 1 字节 air 位图 |
| `0xB2` + 96 字节 | 设置 LED（32 格 × RGB） |
| `0xB3` | 读配置 |
| `0xB5` | 重置配置 |

传感器值是**模拟量**（0~255），是否判定为"按下"由上位机决定。

## 九、排错

| 现象 | 处理 |
|---|---|
| `找不到手台` | 看 `ls /dev/serial/by-id/`，确认插好、权限对 |
| 中继起来了但 `游戏请求 0/s` | COM 号不匹配，确认游戏用的是哪个号 |
| 又开始"慢半拍" | 多半是设备重新枚举导致映射悬空，重做第三节 |
| `丢弃` 在涨 | 有别的进程在抢这个端口，关掉网页配置工具 |
| 中继退出后游戏打不开串口 | 检查 `com3` 是否被还原成原值 |
